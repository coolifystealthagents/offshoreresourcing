## Research question and decision supported

The question is what share of offshore shift handover notes leave an open item without a specific next action. The decision supported is whether the handover format, the queue, or the shift review needs repair before the next busy period. A note can be complete as a status summary and still fail as an operating handoff. The method measures the note against the next person's ability to start work, not against the length of the document.

State whether the sample covers one queue, one client, or all queues handled by the team. A note that works for a simple ticket queue may fail for a finance process with approvals and cutoffs. Report the scope beside the rate so a reader does not apply the result to work it never covered. The decision should follow the scope that produced the finding.

## Define a usable next action

A usable next action names the specific step, the owner, and the point by which it should happen. Waiting for customer, in progress, or pending review are statuses, not next actions. The action should be clear enough that a person unfamiliar with the case can start it without reading the full history. If the next step depends on a decision, the note should name the decision owner and the question. A note that says escalate without naming the escalation path is incomplete under this definition.

Write two examples of a usable action and two examples that look specific but are not. Review them with the shifts before sampling so the reviewers apply the same standard. Keep the examples with the coding sheet. A definition that lives only in a meeting will drift as soon as a new lead joins.

## Draw the sample

Select handover notes from a defined period and include every shift and queue in scope. Sample days rather than only notes that mention problems, because a quiet-looking handover may hide an unassigned action. Include the start and end of the week and any shift that follows a holiday. Record the note date, queue, author, and number of open items. If the volume is low, review every note and report the count rather than a percentage.

Stratify by queue and shift so one large queue does not dominate the result. Check that the sample includes notes written by regular staff and by temporary coverage. A sample drawn only from the most experienced lead will understate the problem. Keep the selection rule so the review can be repeated after the format changes.

## Measure missing actions by item

Use the open item as the unit and count how many lack a usable next action. Report the number of notes, the number of open items, and the number of missing actions. A note can have one missing action and still be mostly complete, so do not turn the note into a pass or fail too quickly. Show the share by queue, shift, and author group. Include the count of items that have an owner but no due point.

Separate a missing action from a missing owner and a missing due point. The three gaps have different fixes. A missing action may be an instruction problem, a missing owner may be a queue design problem, and a missing due point may be a format problem. Report them separately before combining them into one handover quality score.

## Separate routine work from decision blockers

A routine item with no next action is a documentation gap, while a decision blocker with no owner is a service risk. Code the items by whether they need a manager decision, a customer response, an access fix, or routine processing. Report the missing-action rate for each type. A lower rate among decision items would be surprising and worth investigating. A higher rate among access issues may point to an ownership problem outside the shift team.

Read a few decision blockers in full and trace what happened next. Did the item wait for the named owner, or did someone else make the decision? A note can name the wrong approver and still look complete. The trace gives the rate an operational meaning that the coding alone cannot provide. Keep the traced examples anonymous in the report.

## Compare by cause and author group

Group missing actions by cause such as unclear queue status, missing source information, late arrival, or an unresolved decision. If most gaps come from late arrivals, the fix belongs at the intake point rather than in the handover template. If most come from one queue, inspect the fields that queue uses. Compare regular staff with temporary coverage, but check the task mix before drawing a conclusion. A new person may receive harder items, not perform worse.

Ask two leads to code the same small sample and discuss disagreements. A disagreement often reveals a vague definition of next action or a queue status that means different things to different people. Revise the examples before changing the training. Record the calibration result and the version of the definition used in the report.

## Test the handover format

Take ten notes with missing actions and rewrite them using the proposed template. Ask a person from the next shift to identify what to do without asking the original author. Count how many items become usable and how much time the rewrite takes. If the template adds length without improving the next action, simplify it. A format that requires a long narrative is a poor fit for a busy shift.

Test the template on a normal queue and on an unusually large one. Check mobile or small-screen readability if the team reads the note on a phone. Confirm that the decision section stays visible when the note is long. The template should make the important fields easy to find rather than rewarding whoever writes the most.

## Use the result to change one control

Choose the most common and most consequential gap and change one control. If the queue does not require a next action at closure of the shift, add that field and review a sample. If the action is present but the owner is missing, change the queue status or the assignment step. If the gap sits with late items, fix the intake cutoff. Assign an owner and a review date, then repeat the sample with the same definition.

Confirm that the change was actually delivered before designing another one. Check the template version, the training note, and the queue configuration. A control that exists only in a document is not a control. Re-measure after a full cycle and compare the same queues and shifts rather than a convenient subset.

## Limitations

The method depends on handover notes that are complete enough to code. A team may write a short note because the queue is visible elsewhere, which can make the note look worse than the operating reality. Reviewers may disagree about whether an action is specific enough, and a new template can create apparent improvement before behavior changes. Small queues and mixed task types make the rate unstable.

A missing action is not proof that no one knew what to do. It may mean the next step was obvious to the shift or recorded in another system. Use the result to locate a documentation or ownership problem, not to judge an individual. Report the sample, the definition, and any change to the queue or template so the next review can interpret the number correctly.
