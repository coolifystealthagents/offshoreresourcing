## Research question and decision supported

The question is how much rework follows a new client transition and whether the rework comes from unclear instructions, missing access, or a genuine change in the client's requirements. The decision supported is whether the transition checklist is working and which part of the handoff needs repair. A first month with high rework is not automatically a failure, because a new client often reveals gaps that were invisible during sales. The method separates learning from avoidable confusion.

State whether the study covers the first month, the first quarter, or a defined set of tasks. A short window may capture startup noise, while a long window may include a real change in scope. Report the period beside the rate and describe any scope change that occurred during it. The decision should follow the period that matches the transition.

## Define rework

Rework is work that must be repeated because the first output did not meet the accepted standard or because the instruction changed after work began. Count a correction separately from a clarification. A clarification adds information before the work is accepted, while a correction changes work that was already submitted. A changed client requirement is a third category, because it is not the team's error. Write two examples of each and review them with the client owner.

A rework count should use the task as the unit and record the reason, the owner who requested the change, and the time spent. Do not count a normal review comment as rework unless it required a substantive repeat. Do not count a change requested by the client as an error by the offshore team. The definitions should be stable enough for two reviewers to classify the same case the same way.

## Build the transition baseline

Record the scope, the access list, the named owners, and the acceptance standard at the start of the transition. Keep the first approved sample as the baseline for what good work looks like. Record the client's definitions of priority, complete, and approved. If the baseline is missing, reconstruct it from the first week's records and mark it as reconstructed. A rate without a baseline cannot show whether the transition improved or simply changed.

## Draw the sample of completed tasks

Select tasks completed during the transition and include every work type in the agreed scope. Include normal tasks, incomplete inputs, and exceptions, because a transition often fails at the edges. Exclude work that was cancelled before any output was produced. Record the task type, owner, date, and whether the task was reopened. If the volume is low, review every task and report the count rather than a percentage.

Stratify by work type and by the person who performed the task. Check that the sample includes the first week and the last week of the transition. A sample drawn only from the final stable week will understate the startup problem. Keep the selection rule with the report so a later review can repeat it.

## Measure rework by cause

Report the rework share by cause such as unclear instruction, missing access, missing source information, incomplete client input, or changed requirement. Separate the causes that the transition can fix from the ones the client controls. Show the count and time for each cause, not only the percentage. A small number of access-related reworks may consume more time than a larger number of formatting corrections. The cause table should point to the next control to change.

Include the task type and the owner in the table. A cause that appears only in one work type may be a documentation problem rather than a general onboarding problem. A cause that appears across every type may point to the transition plan itself. Read a few examples in each cell before deciding what the pattern means. Record whether the rework was detected by the client or by the offshore reviewer, because a client-detected error may reach the customer before the team can correct it. That distinction helps the transition owner prioritize the controls that protect the client relationship.

## Separate learning from avoidable rework

A new team will need time to learn the client's vocabulary, systems, and examples. Some rework in the first week is expected and should be treated as training cost. The avoidable share is the rework caused by missing access, contradictory instructions, or a missing owner. Code the cases accordingly and report both. The target is not zero rework, because a useful review can still find a real defect. The target is a declining avoidable share as the team learns.

Ask the offshore lead and the client owner to classify a small overlapping sample. Discuss any case where one sees learning and the other sees a process failure. The discussion clarifies the boundary and may reveal an instruction that was never delivered. Keep the agreed examples with the transition record.

## Test one transition control

Take the most common avoidable cause and change one control. If access is the cause, add an access test before the first live task. If the instruction is unclear, add a worked example and a short review. If the client input is incomplete, add a required field to the intake. Test the change on a new task or a new client and compare the same cause category. Do not change several controls at once, because the result will not show which one helped.

Confirm that the change was actually used. Check the checklist version, the access record, and the client's intake form. A control that exists only in the transition document is not a control. Measure the same task types and the same period length so the comparison is fair.

## Use the result to close the transition

At the end of the review, record whether the transition should close, continue with a correction, or pause for a scope decision. Name the owner of each open action and the date it will be reviewed. Update the scope with any work that was added or removed. Keep the baseline and the first review together so the next client transition can reuse the lesson. A transition that closes without a written decision tends to reopen informally later.

Share the result with the client in plain language. Focus on the cause and the fix rather than on a score. Ask whether the client saw the same pattern and whether any requirement changed during the period. The client's view may explain a rework category that the internal record cannot. Record the response and the agreed next step.

A short transition close should state the rework share, the main avoidable cause, and the control that will change. Keep the baseline and the first review in the same file so the next transition can reuse the lesson. Do not present the rate as a performance grade for the offshore team. The useful question is whether the next client transition produces fewer avoidable corrections.

## Limitations

The method depends on task records that show when work was reopened and why. A team may correct work in a chat message without recording it, which will understate rework. Reviewers may disagree about whether a change is learning or a process failure. A new client may also change requirements during the transition, making the baseline unstable. Small volumes and mixed task types limit the precision of the rate.

A high rework rate is not proof that the offshore team performed poorly. It may show that the transition plan or the client's inputs were incomplete. Use the result to improve the handoff, not to judge an individual from one month. Report the period, the definitions, and any scope change so the next review can interpret the number correctly.
