An escalation is supposed to move a decision to the person who has authority to make it, but many escalations arrive as a description of a problem rather than a decision request. A manager then spends time reopening the record, asking for the missing field, and restating the rule before the real question can be answered. This report defines a reproducible way to sample escalations and code whether they contain the evidence a manager needs. The method is a review aid, not a claim about how often any particular team fails, and it should be adapted to the role's own approval rules.

## Research question and decision supported

The question is whether an escalation gives the manager enough evidence to decide without a follow-up round trip. The decision supported is whether the team should change the escalation template, add a training example, or adjust the approval threshold that sends work upward. A second decision is whether the current escalation volume reflects real exceptions or a queue that lacks the information to resolve ordinary cases. Write the answer as a coded sample with a small set of evidence fields, not as a general impression from a few memorable messages. The report should name the queue, the period, the roles included, and the approval rules that applied. It should also state whether the sample covers only written escalations or includes chat and verbal requests that were later recorded.

## Define the evidence standard for an escalation

Start from the written decision rights for the role. An escalation should identify the item, the action requested, the rule or threshold that makes the action exceptional, and the person who can approve it. It should also show the source record that the manager would need to verify the request, or a precise pointer to that record. If any field is missing, the escalation has shifted work back to the manager rather than moving a decision forward. Separate mandatory fields from useful context. A customer's account history may help, but the manager usually needs the specific order, the requested change, the amount, and the approval limit. Define the minimum set with the people who actually approve the work, because a template written only by the queue team may omit the field the approver checks first. Publish the standard before the sample so coders are not inventing criteria after they see the messages.

## Sample and coding approach

Draw the sample from the escalation queue rather than from the manager's inbox, because the inbox may exclude requests that never reached the right person. Include a full week or a complete cycle, and stratify by request type, shift, and approver where the volume allows. If the queue is small, extend the period rather than adding unrelated work to reach an arbitrary count. Use two coders on a shared subset before coding the full sample. Each coder records whether the item identifier, requested action, rule citation, source evidence, and named approver are present. Discuss disagreements on the actual message, then revise the codebook if a field is ambiguous. Keep the raw messages in a restricted location and report only the coded pattern in the summary.

## What to measure in each escalation

Count each required field as present, absent, or unclear, and record the time between the escalation and the manager's first substantive response. That response time is not a performance score for the manager; it shows whether the escalation could be answered on the first pass. Add the number of follow-up messages needed before a decision, because a short first reply that asks three questions is still a round trip. Record the outcome as approved, denied, returned for more information, or routed to another owner. This separates an escalation with poor evidence from one that reached the wrong authority entirely. Also note whether the same item had already been escalated once, since repeated escalation can signal a rule that is hard to apply rather than a person who writes poorly.

## Common evidence gaps and what they cost

The most common gap is a missing rule citation, which forces the manager to infer why the item is exceptional. The second is a missing source record, which forces a search across systems before the decision can begin. The third is an open-ended question such as what should we do, which transfers the framing of the decision back to the manager. Each gap adds a cycle that may not appear in the queue's response-time report. A gap is not automatically a worker failure. The source record may be unavailable to the role, the approval rule may be unclear, or the queue may not provide a field for the needed evidence. Code the likely cause separately from the missing field so the repair can target the system or the instruction. A team that only coaches individuals will keep seeing the same gap when the underlying form never asks for the missing item.

## Testing the effect of a template

If the team changes the escalation template, compare a pre-change sample with a post-change sample using the same fields and the same coding rules. Allow time for training and for the queue to adjust before drawing a conclusion. Report the change in follow-up rounds and time to decision alongside the field completeness rate, because a template can increase completeness while adding length that slows the response. Use a small controlled pilot if the queue permits it. Apply the template to one request type or one shift, then compare it with a similar lane that still uses the old form. This is not a formal experiment, but it gives a clearer signal than a before-and-after comparison during a period when volume or staffing also changed. Record those concurrent changes in the report.

## Controls before changing the escalation rule

Check that the escalation path still matches the approval authority. A complete message sent to a person who cannot approve the action will still wait. Confirm that the named approver is available during the shift, that a backup is named, and that the queue records the handoff. The evidence standard should support the authority map, not substitute for it. Protect sensitive content by defining what evidence may be copied into the escalation and what must be referenced in place. A manager may need to see an account record without needing a full identity document in chat. Use the least data necessary to support the decision, and keep the escalation record under the same retention rule as the case.

## Limitations and reporting

Coded completeness measures the presence of fields, not the quality of the judgment behind them. A message can contain every field and still ask for the wrong decision. Pair the coding with a small qualitative review of strong and weak examples, and state that the sample reflects the chosen period rather than the whole operation. Avoid turning the field score into an individual performance rating. Report the queue, period, sample size, coding rules, inter-coder agreement, and the main gaps with counts. Add a short list of recommended changes with an owner and a review date. Repeat the sample after the change and compare the same measures so the next reviewer can see whether the repair actually reduced the follow-up burden.

## What a manager actually checks first

Most approvers follow a stable order even when the escalation does not: confirm the authority, confirm the amount or scope, confirm the source record, then check the customer consequence. Write that order down and compare it with the fields in the template. If the template puts background before the amount, the approver has to scan past information that does not change the decision. A short header with the requested action, the threshold, and the record link reduces that scan. The rest of the message can carry context without blocking the first check. Reviewing a few real approvals with the manager is the fastest way to learn this order.

## Separating an escalation from a status update

A status update tells the reader what happened, while an escalation asks for a decision that the worker cannot make. Mixing the two in one channel makes the urgent requests hard to find and trains managers to skim. Give escalations their own queue, subject line, or tag, and require the decision request in the first line. Status updates can then stay in the case record without competing for the same attention. If the team uses chat, pin the escalation format and route routine updates elsewhere. This separation also gives the audit a clean population to sample.

## Coaching the note without rewriting it

When a reviewer rewrites an escalation, the worker learns the answer but not the pattern. Instead, point to the missing field and ask the worker to add it before the message is sent. Use two examples from the same week, one complete and one incomplete, and ask the team to identify the difference. Keep the coaching focused on the evidence, not on writing style. A short monthly review of anonymized examples is usually more effective than a long policy reminder. Record the recurring gaps so the template can be improved instead of coached around.

## A small scorecard for escalation quality

Score each escalation on four checks: the decision request is explicit, the rule or threshold is named, the source evidence is reachable, and the approver has authority. Add a fifth check for timeliness only if the queue has a written response expectation. Report the checks separately so a team can see whether the problem is framing, evidence, or routing. A single total hides the difference between a well-written request sent to the wrong person and a vague request sent correctly. Use the scorecard for process review, not as an individual rating. Recheck the same four fields after a template change.
